The rules that keep this from rotting

  1. Work goes in the ledger, not in a new chapter. A bug, a gap or a "we should later" becomes a ticket in documentation/tickets.jsonl. The chapter count is capped at 13 by the documentation contract; date-stamped filenames are rejected.
  2. A section is rewritten in place. When the product changes, edit the section that owns it, not a new record of the change. Git history is the change log; the document is the current truth.
  3. A closed ticket needs proof. status: closed is rejected without verified_by naming the command that proved it and the date it ran.
  4. Closed tickets stay in the file. They are the searchable history: "did we ever look at this?" is answered months later without reading old chapters.
  5. A section declares what it covers. covers: lists the code paths a section describes, with a repo prefix. A section whose covered code moved is stale until it is re-read.
  6. Old chapters are archived, never deleted. The pre-2026-11 chapter files are kept in git history; their content is folded into the sections above.

Context and goals

What the system is for

HTML-Notes is a local-first knowledge journal with a chat-driven canvas. The user asks a question in the journal; a fast lane classifies the ask, an LLM router picks a path, the shared lazy-agent-service runtime answers, and the server renders one or more widgets (news card, stock card, weather, checklist, clock, KPI, table, timeline, music player, YouTube CRT) onto the canvas. The canvas and its notes are stored in the local SQLite database, and a saved canvas re-renders from stored state rather than from the chat transcript.

The product is deliberately narrow: it renders a constrained set of widgets from server-side templates, it keeps the notes and chat history on the operator's own machine, and it does not pretend to be a general web app builder.

Out of scope

Not in scopeWhy
A free-form HTML/JS generatorEvery widget comes from app/widgets/factory.py; arbitrary agent HTML is not rendered.
The lazy-agent-service runtime itselfIt is a separate service; HTML-Notes integrates through its HTTP API.

Cloud model hostingThe router and agent calls go to the local vLLM boxes through the shared runtime.
A multi-user SaaS deploymentThe app is local-first, single-operator and LAN-scoped.
Long-term analyticsThe canvas is a journal, not a BI product.

A goal is only real if a check enforces it. Section 09 names the check behind each claim; this chapter states what the product is trying to guarantee.

Contract ownership

CONTRACT_OWNERSHIP.md records which side owns each boundary: the server owns the widget factory, the canvas owns placement, the client owns only transient UI state (drag, hover, playback carry), and lazy-agent-service owns the agent runtime and tool catalog. A change that crosses a boundary updates the owner's contract and its tests, not just the caller.

Users and surfaces

  • The journal UI at app/static/index.html: chat, canvas, notes and the widget manager.
  • The HTTP API in app/routes/: sessions, messages, notes, watches, health and internal quality endpoints.
  • The documentation site: this set of chapters rendered by documentation/build_docs.py.

Execution pipeline

One chat turn runs through five ordered stages. Every stage has a deterministic fallback, so a missing model degrades the answer instead of emptying the canvas.

Stage 0 — Ingest

POST /session/message (app/routes/message.py) receives the user message and the session id. The route opens the SSE response, records the user message in chat_messages, and loads the session context (recent turns, the current canvas, the active note). The route is the only writer of the chat transcript.

Stage 1 — Classify and route

The fast lane inspects the message before any model call:

  • A music-shaped ask (a play verb plus a subject, or a medium word) sets music_fallback and skips the list/notes/compose/answer/build lanes.
  • A news ask goes through classify_news_ask, which recognises topic asks and named live networks.
  • Video/live asks keep their deterministic override; the router does not get to turn "cnn live news" into a news card.
  • Everything else reaches the LLM router, which returns a path plus modifiers (including modifiers.kind for music).

The router catalog uses placeholder examples only. Real names in the catalog make the model copy an example into the query (the "heavy metal music → buckethead" failure). music_query_grounded then rejects a router subject that shares no word stem with the message, so a typo fix such as "coletrain" → "John Coltrane" survives while an invented subject does not.

Stage 2 — Agent and tools

The selected path calls the shared runtime through app/adapters/runtime/: /agent for a chat turn, /models and /health for admission and health. The agent may call the runtime's tools (news search, scraper, embedding); HTML-Notes does not execute arbitrary agent HTML. The runtime answer is parsed into a widget plan: a widget type plus its data fields.

Stage 3 — Research and evidence

When the ask needs current facts, the research coordinator (app/services/research/coordinator.py) dispatches workers from app/services/research/workers/ (news, price, peer/sector, primary source, skeptic). Evidence lands in research_evidence with its source, and the synthesizer writes an answer version. The budget module caps the number of worker calls and the wall time; a capped run returns the evidence it has instead of failing.

Stage 4 — Render

app/widgets/factory.py renders the chosen widget from server-side templates. The factory stamps the widget's config as strict JSON in data-hn-config next to the Alpine state, so the client can rebuild the same widget later without guessing defaults. The SSE stream emits the widget frame, then the assistant message.

Stage 5 — Persist and repair

app/canvas_manager.py places the widget on the canvas and serializes the canvas into the note row. The client (app/static/js/widgets.js and app/static/index.js) mounts the widget, wires resize and messages, and runs the self-heal path:

  • musicWidgetNeedsRebuild rebuilds only when the Alpine wiring is missing or in the old positional form, and rebuilds from data-hn-config.
  • The clock self-heal keeps the server's clockWidget(tz, …) call instead of forcing 'local'.
  • WidgetResizer skips device-style widgets (.youtube-player, the Walkman card) and derives their height from their width.

Music fast lane, in detail

flowchart TD
  A[ask] --> B{"music-shaped?"}
  B -- no --> O[other lanes / router]
  B -- yes --> R["route_with_llm (subject + kind)"]
  R -- "within MUSIC_ROUTER_BUDGET_S (1.5 s)" --> W["router widget: query = subject, kind = artist|genre"]
  R -- "slow / down / small talk / defer" --> F["fallback player now: subject from the message, kind from the genre list or ''"]
  F --> L{"router answers within MUSIC_ROUTER_REFINE_S (25 s)?"}
  L -- "yes, different" --> X["same widget rebuilt in place (router-refine)"]

Knobs live in app/config.py: MUSIC_ROUTER_BUDGET_S (default 1.5) and MUSIC_ROUTER_REFINE_S (default 25). The builder trusts the router's query (it does not re-strip the raw message), and the old "lofi" default is gone; an empty kind means the music service's own default mix.

Turn termination

A turn always ends with one of: a rendered widget plus message, a text answer, or an error card. The assistant message is written even when rendering fails, so the session history and the routing eval remain complete.

  1. Routes never contain widget HTML. A route resolves data and calls the factory; the factory owns markup.

The research stack is the only multi-worker service in the app:

Domain features

News and research

The news pipeline is evidence-first:

  1. Collect candidate stories from the configured feeds and the shared search service.
  2. Gate them for relevance; a story that fails the gate never reaches the card.
  3. Resolve links: Google News RSS links (news.google.com/rss/articles/CBMi…) never redirect server-side. app/services/search.py decodes them to the publisher URL with Google's batchexecute (8/8 live, about 1 s), so the card links point at the publisher rather than the redirector.
  4. Summarise: each vetted story is scraped in its own call (_attach_article_bodies), so one slow site loses only itself. On a gated topic ask the editor cannot drop a story; any story it skips is summarised on its own (_summarize_sources_individually).
  5. Render the news card with the vetted stories and their summaries.

A topic card reads article bodies, not ~200-character provider snippets. The live "news about ai regulation" check returns 3 vetted stories and 3 summaries (before the fix: 1), in about 23 s.

Live news networks

app/services/youtube_helpers.py has a _NEWS_NETWORKS table (patterns, official channels, handles). is_network_live_ask catches "put on / tune in / watch <network>", so the news pre-router does not turn those into a headline card. pick_news_network_live tries, in order:

  1. the channel's /@Handle/live page (canonical watch?v= plus "isLiveNow":true);
  2. an official-channel live search;
  3. an honest fallback titled "<Network> isn't live on YouTube right now — latest: …".

A named network plays its own live stream, never a look-alike channel.

Music asks

Music is the most exercised lane, and its rules are recorded in section 10:

  • The fast lane detects a music-shaped ask; the router understands the subject and the kind.
  • The builder trusts the router's query and does not re-strip the raw message.
  • resolve_music_kind answers "genre" only for an exact MusicBrainz genre (app/domain/musicbrainz_genres.txt, CC0, 2,220 names), else "". A "last word is a genre" rule was dropped because "instrumental" is a listed genre.
  • The router debug frame carries modifiers; a late answer emits {"path": "router-refine", "config": {genre, kind}} and rebuilds the same widget in place.
  • History posts the music-player PlayEvent shape (buildPlayEvent; track_id = youtube://<id>) and maps /history/recent rows (mapServerHistory).

UI and widgets

The canvas

The canvas is an Alpine-driven grid in app/static/index.html. Every widget is a card in that grid; the canvas manager owns its column span and its serialized state. The client mounts widgets, wires their actions and keeps transient UI state.

The widget lifecycle is:

  1. Render — the server sends a widget frame with its HTML and data-hn-config.
  2. Mount — app/static/js/widgets.js initialises the widget's Alpine component.
  3. Act — a click, resize or message updates the widget locally and posts the action to the server when the server owns the state.
  4. Persist — the server updates the canvas row.
  5. Repair — on reload, the self-heal path rebuilds a widget whose Alpine wiring is missing, from data-hn-config.

Widget factory

app/widgets/factory.py is the only place that produces widget HTML. Each render function:

  • takes typed data (never raw model prose as HTML);
  • escapes text and attributes;
  • stamps data-hn-config as strict JSON next to x-data;
  • uses classes that exist in the compiled Tailwind build.

app/presentation/widgets/catalog.py is the registry of widget types. A type that is not in the catalog cannot be requested by the model.

HUD theme and boxless devices

app/static/hud-theme.css draws every widget as a holographic panel: an octagon cut with clip-path, a 2 px hover lift, and cyan L-shaped corner brackets on ::before. Two widgets are real objects, not panels, so the BOXLESS WIDGETS rule in app/static/index.css opts .widget-container.youtube-player and the Walkman's .widget-container.music-widget-root out of all of it:

  • fill, border, radius, shadow and backdrop filter are cleared with !important (the frame rule is itself !important);
  • clip-path: none !important and transform: none !important, so the octagon and the hover lift cannot slice or slide the device;
  • ::before and ::after are removed, so brackets and the update light-sweep do not float over the device;
  • the same-origin card iframe is transparent with no border.

Tailwind is compiled at build time

Nothing Tailwind runs in the browser. app/static/tailwind.css (about 47 KB minified) is built by the Tailwind CLI (tailwindcss@3.4.17, the same v3 engine as the old CDN, stock config, Preflight included):

  • in the Docker image, by the css stage in Dockerfile;
  • locally, by npm run build:css (also before npm run dev / npm start).

tailwind.css is linked as the last stylesheet in <head>, so the cascade order is unchanged, and it is cache-busted like index.css (_CACHE_BUSTED_ASSETS). tailwind.config.js scans app/**/*.py and app/static/**/*.{js,html}; the safelist (tailwind.safelist.json) holds 771 class tokens mined from canvases in the live notes.db by scripts/mine_tailwind_safelist.py, covering classes older templates and agent cards used that the current source no longer has.

A class assembled at runtime from pieces (f"text-{tone}-400") is caught by tests/test_tailwind_build.py; spell it out in source or add it to the safelist.

Decisions

Settled choices. Changing one means editing this page with the evidence that reversed it, not silently diverging.

DEC-001 — Only the music lane goes through the LLM router

The router turned "cnn live news" / "bloomberg live news" into a news card (11/17 on video asks) — the exact failure the deterministic video/live override exists to prevent. News (10/12) already runs through classify_news_ask (app/main.py). Video and news keep their deterministic lanes until the router beats them on tests/routing_eval.json. Consequence: the router catalog only has to be right about music and chat; music asks are gated by the fast lane in app/routes/message.py before any model call.

DEC-002 — Show the fallback player now, refine it in place

Blocking variants either added 4 s for nothing or gained nothing, because the shared local boxes (Jetson nemotron35, Gold Spark DeepSeek) are saturated by other agents. The fallback player starts immediately with a subject taken from the message; a router answer within MUSIC_ROUTER_REFINE_S (25 s) rebuilds the same widget via the router-refine debug path. Consequence: users hear the wrong thing briefly on the ~8% the router gets wrong, rather than hearing nothing for 4 s.

DEC-003 — No live MusicBrainz artist lookup

Measured 0.6–9.3 s per call and noisy (smooth jazz → artist "Smooth Jazz Band", score 100). resolve_music_kind answers "genre" only for an exact match against the checked-in list app/domain/musicbrainz_genres.txt (CC0, 2,220 names); anything else is "" (genre-first mix). The "last word is a genre" heuristic was dropped because "instrumental" is a listed genre.

DEC-004 — Router output carries modifiers.kind only; no subject_type, no confidence

modifiers.kind is the only consumer, and extra output tokens cost latency on every route. The catalog uses placeholder examples only — real example names get copied into the query ("heavy metal music" → query "buckethead"). Grounding is server-side: music_query_grounded (app/main.py) drops a router subject that shares no word stem with the message.

DEC-005 — Tailwind is compiled at build time; nothing Tailwind runs in the browser

The CDN runtime (~3 MB, production warning on every load) is replaced by app/static/tailwind.css (~47 KB) built by the Tailwind CLI (tailwindcss@3.4.17) in the Docker css stage and by npm run build:css locally. It is the last stylesheet in <head> so the cascade is unchanged (verified by 0-pixel screenshot diff). Dynamic classes are covered by tailwind.safelist.json — 771 tokens mined from live canvases in notes.db by scripts/mine_tailwind_safelist.py — and enforced by tests/test_tailwind_build.py.

DEC-006 — The server owns widget config; the client rebuilds only from data-hn-config

The factory stamps strict JSON data-hn-config next to the Alpine state. Self-heal (musicWidgetNeedsRebuild / recoverMusicWidgetConfig in app/static/index.js) rebuilds only when the Alpine wiring is missing or in the old positional form, and rebuilds from that config, never from a guessed default. The 2026-11-03 "buckethead plays Duke Ellington" bug was a self-heal inventing genre = 'jazz'; the clock heal once forced 'local' over the server's tz. A widget with no config is left as-is and reported.

DEC-007 — Device-style widgets are boxless and self-resizing

The Walkman music card and the Sony Trinitron CRT card are rendered objects, not panels: the BOXLESS WIDGETS rule in app/static/index.css clears frame, clip, hover lift, brackets and the light-sweep for them; WidgetResizer skips them, their height is derived from width (round(width / 1.8182) for the CRT), and the drag target is the device's own bezel. A stationary click (≤ 3 px) is not a resize; only {cols} is persisted. Consequence: the HUD theme must never gain a global rule these two cannot opt out of with !important.

DEC-008 — History is posted in the music-player's wire format, not ours

buildPlayEvent (app/static/js/widgets.js) posts the exact PlayEvent shape music-player validates (id, track_id, timestamp, duration, completion_rate, source, context), with track_id = youtube://<id> as the music-player web app records it, and mapServerHistory reads the bare list /history/recent returns. The 422 on every track (2026-11-03) came from inventing our own body.

DEC-009 — The shared runtime is the only model surface

All model calls go through app/adapters/runtime/ (/agent, /models, /health) with the same attribution headers (x-project / x-username) as /agent; probes without them logged as anonymous. HTML-Notes never executes arbitrary agent HTML and never holds model credentials itself.
